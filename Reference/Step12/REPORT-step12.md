# Отчёт по этапу 1: изоляция памяти — Sv39 MMU + PMP

## 1. Цель этапа

Наделить микроядро двухслойной защитой памяти:

- **MMU (Sv39)** — виртуальная трансляция в S/U-mode, identity-маппинг RAM, контроль прав на уровне страниц (R/W/X, U);
- **PMP (TOR)** — физический барьер для U-mode: только код ядра (R|X), таблицы страниц (R) и собственный стек задачи (R|W) доступны непривилегированному коду;
- **trap-обработчик**, который различает, какой рубеж поймал нарушителя, и корректно возвращает управление в M-mode Shell.

## 2. Что сделано

| Компонент | Содержание |
|---|---|
| `src/mm/mmu.c` | Инициализация Sv39: L1@`0x80004000`, L2@`0x80003000`, identity 1 ГиБ от `0x80000000`, включение `satp` |
| Linker script | Отдельная секция `.pgtables` (2 таблицы = 8 КБ) с символами `kernel_pgtables_start/end` |
| `src/arch/pmp.c` | TOR-цепочка из 7 записей: запрет `[0, text)`, R|X на код, запрет до таблиц, R на таблицы, запрет до ustack, R|W на ustack, запрет до конца RAM |
| Trap-обработчик | Классификация причин 12/13/15 (page faults) наравне с PMP-нарушениями 1/5/7; оба пути завершают U-процесс и возвращают Shell |

## 3. Разбор багов (симптом → причина → фикс)

**Баг 1. Артефакты сборки в git.** `bin/` попал в репозиторий — живой код и стейджинг-артефакты смешались. Фикс: `.gitignore` + очистка. Урок: место жительства артефакта определяется там, где он потребляется, — и оно не в git.

**Баг 2. «Мёртвый» код из-за комментария.** Инициализация кучи была закомментирована при правке; ядро формально работало, кучи фактически не было. Фикс: восстановление вызова. Урок: симуляция комментария — самый тихий вид деградации, ловится только прогоном с контрактными выводами.

**Баг 3. IAF в U-mode — неверный первый диагноз.** Симптом: Instruction Access Fault на входе в U-задачу. Первая гипотеза «PMP запретил код» оказалась ложной: истинная причина — U-код не мог **прочитать таблицы страниц** для обхода MMU (фетч трансляции идёт с правами исходного доступа). Фикс: TOR-регион R на `[pgtables_start, pgtables_end)` в `pmp_configure_user`. Урок этапа: **не доверять первому объяснению, пока числа не сойдутся во всех точках** — `mcause`, `mepc`, `mtval`, вывод конфигуратора.

**Баг 4. Эволюция нарушителя.** По мере закрытия дыр `pmptest` менял место падения: PMP на фетче → запрет записи в UART. Финальное поведение — нарушитель исполняется, честно печатает намерение и ловится **MMU** (`mcause=15`, Store Page Fault, `mtval=0x10000000`), потому что проверка трансляции в Sv39 стоит перед PMP. Это первый заработок двухслойной обороны: unmapped VA рубится на входе.

**Баг 5. Мёртвый код `pmp_configure_user_strict`.** Функция существовала, но демки вызывали старую `pmp_configure_user` — регион таблиц не попадал в активную цепочку. Фикс: вживление региона в основную функцию, строгая версия очищена от мёртвых UART-записей (вывернутый TOR-диапазон при `0x10000000 < heap_end`).

## 4. Верификация (эталонный прогон)

- `info` — диагностика: RV64GC, UART0 `0x10000000`, SP ядра.
- `mem` / `memtest` — коалесценция до единого блока; Double-Free, unaligned, out-of-bounds — все пойманы.
- `usermode` — полный цикл U-mode: печать, ecall `SYS_GET_TICKS`, `SYS_EXIT(0)`, возврат в Shell.
- `sched` — Round-Robin, 2 U-задачи, 6 квантов таймера, переключение контекстов, освобождение памяти.
- `pmptest` — rogue исполняется, печатает намерение, ловится MMU: `mcause=15`, `mtval=0x10000000`, ядро возвращено в M-mode Shell.
- `exit` — штатное завершение.

Все гейты CI (`build-and-sast`) зелёные с первой итерации: gitleaks (338 КБ, утечек нет), clang-format (dry-run, 26 файлов), cppcheck (warning/style/performance/portability, 12 файлов), clang-tidy (`--warnings-as-errors='*'`), сборка (`kernel.bin` ~12K, `kernel.elf` ~71K), публикация артефакта с ротацией 10 версий.

## 5. Ключевые инварианты этапа

1. **TOR-цепочка читается только целиком**: нижняя граница записи N — это верхняя граница N-1. Одиночная правка середины сдвигает соседей — карта меняется полным перестроением.
2. **Обход таблиц с правами исходного доступа**: MMU читает PTE с правами исходного доступа — для U-фетча таблицы обязаны быть читаемы в U-mode. R без W: писать в таблицы пользователь не должен; ядро в M-mode проходит мимо PMP.
3. **M-режим не ограничен**: бит `L` в `pmpcfg` не ставится — ядро продолжает писать в UART и кучу.
4. **Порядок рубежей**: сначала MMU (unmapped VA → page fault 12/13/15), потом PMP (mapped, но запрещённое → access fault 1/5/7).
5. **MPP-гигиена в трапах**: тик, заставший CPU в M-mode, не сохраняет контекст в таблицу задач; планировщик явно назначает режим возврата (`csr_set_return_mode`).

## 6. Известное ограничение

S-mode в `satp` включён, но собственный S-обработчик пока не разделён — все исключения идут в M-mode (medeleg выключен). Нормально для этапа 1; будет пересмотрено на этапе 2 при переходе к per-process VAs.

## 7. Резюме

Этап 1 закрыт: микроядро получило **работающую двухслойную защиту памяти** — Sv39 с identity-маппингом и TOR-PMP, согласованные через linker-символы секции `.pgtables`. Полный контракт (`info`, `mem`/`memtest`, `usermode`, `sched`, `pmptest`, `exit`) проходит в эталонном виде, включая демонстрацию отлова нарушителя на MMU-рубеже с точным `mcause`/`mtval`. Все DevSecOps-гейты — зелёные с первой итерации.

Пройдены три нетривиальных отладочных кейса (артефакты в git, мёртвый код, IAF с ложным первым диагнозом). Главный результат этапа — не сама защита, а **отработанный метод**: симптом → улики → пересмотр диагноза → фикс → контрактный прогон.

## 8. Дальнейшие шаги (этап 2)

- `mmu_map_page(vaddr, paddr, perms)` — постраничный проход L1→L2→L3 с записью PTE;
- копия кода задачи на VA `0x4000000000` + маппинг её ustack;
- снятие бита `U` с identity-мегапейджа; контрольный тест: фетч по `0x80000540` из U-mode даёт page fault 12, а не исполнение.
